# Architecture

## Overview

AISafety.com is a **Next.js 16 (App Router) + TypeScript** app on Vercel. The public pages are prerendered at build time from one Airtable base. Around them sit a public read-only Data API, a chatbot, first-party analytics, and a password-gated admin area. Nearly all of the code is written with Claude Code; `CLAUDE.md` at the repo root holds the conventions, this file explains how the pieces fit.

## The big picture

```
 Visitor's browser
   │ static pages · chatbot (SSE) · /api/track beacon · Data API
   ▼
 ┌──────────────────────── Next.js on Vercel ─────────────────────────┐
 │ src/app/*                 pages, prerendered from src/lib/data     │
 │ src/app/api/v1/*          public Data API (src/lib/api)            │
 │ src/app/api/assistant     chatbot ──────────────▶ Anthropic API    │
 │ src/app/api/track         analytics beacon ─────▶ Upstash Redis   │
 │ src/app/admin/*           queue · analytics · chat log ·           │
 │                           map editor · preview · newsletter        │
 │ src/proxy.ts              AI-assistant fetches ─▶ Matomo           │
 │ crons (vercel.json)       check-rebuild · check-catalog · themes   │
 └────────────────────────────────────────────────────────────────────┘
   │ reads (hourly cache)        │ attachments, transcripts
   ▼                             ▼
 Airtable base               Vercel Blob
 (source of truth)           (permanent image URLs)
```

## Data layer: `src/lib/data`

- **One module per Airtable table**, each exporting a typed `getX()` (`getEvents`, `getJobs`, `getMapData`, …). A module declares `TABLE_ID`, an optional `VIEW_ID`, and a `FIELD` map of **permanent field IDs** with the field names as comments. Records are fetched with `returnFieldsByFieldId`, so renaming a field in Airtable changes nothing here.
- **What is live:** `publishedFormula(publishId, hideId)` = Publish? checked and Hide? unchecked. Every public read uses it.
- **`fetchAirtableRecords`** (in `airtable.ts`) does pagination, retries, and pacing to stay under Airtable's five requests per second, and wraps the read in `unstable_cache` for one hour under the tag `airtable-records`. Field helpers (`fieldString`, `fieldNumber`, `fieldStringArray`, `fieldText`, `fieldAttachmentUrl`, `fieldDateOnly`, `fieldFeatured`) coerce the untyped values.
- **Attachments are mirrored to Vercel Blob** (`mirrorAttachments`, prefix `airtable/`). Airtable's own attachment URLs are signed and expire within hours, so they must never reach a cached page or an API response. Without `BLOB_READ_WRITE_TOKEN` the code warns and falls back to the expiring URLs, which is fine for a local dev session.
- **Contributor mode** (`public-api.ts`): with no Airtable credentials, every `getX()` fetches the same objects from the live site's Data API instead, minus the internal curation fields. Anyone can run the site locally with no secrets.
- Cross-cutting logic lives in dependency-free modules next to the data layer: `featured.ts` (featured slots and the events/training queue), `placements.ts`, `filter-counts.ts`, `training-order.ts`, `format-date.ts`, `utm.ts`, `search.ts` with `data/search-index.ts`.

## Pages: `src/app`

- `page.tsx` is a **server component**: it awaits `getX()` and `fetchLastUpdated()`, renders `PageHeader`, and hands the listings to a **client component** (`EventsClient.tsx`, `JobsClient.tsx`, …) that owns filters, sorting, and click tracking. Nothing in the browser talks to Airtable.
- `export const metadata = pageMetadata(SITE_PAGES.x)`. `src/lib/site-pages.ts` is the one list of public pages (title, description, nav icon); `pageMetadata()` turns an entry into `<head>` tags and each route's `opengraph-image.tsx` renders the link-preview card from the same entry (`src/lib/link-preview`).
- `sitemap.ts` lists the public routes; `next.config.ts` holds every redirect, including the old Webflow paths.
- The root `layout.tsx` wraps pages in nav, footer, the Matomo script, the preview banner, and the chatbot widget (`src/components/assistant`).

## Freshness: builds, revalidation, preview

- Pages are static, so the site is only as fresh as its last build. A Vercel cron calls **`/api/check-rebuild` every minute**. For each table in its `TABLES` list it asks Airtable whether any published row changed since `BUILD_TIME` (`hasChangesSince` in `changed-since.ts`, using `LAST_MODIFIED_TIME()` so same-day edits are not lost). If one did, it clears the `airtable-records` cache tag so runtime readers (chatbot catalog, search index, Data API) refetch, then POSTs the Vercel deploy hook, with cooldowns so a burst of edits triggers one build. An Airtable edit is live in about two to three minutes.
- **Preview mode:** `/admin/preview` turns on Next Draft Mode for that admin's browser. With the Draft Mode cookie, `fetchAirtableRecords` skips the cache and reads Airtable live; identical reads within two seconds share one request (`shareLiveRead` in `src/lib/preview.ts`). `PreviewAutoRefresh` polls `/api/admin/preview/changed` every two seconds and refreshes the page when something changed. `scripts/pin-preview-keys.mjs` runs before every build and derives the Draft Mode keys from `PREVIEW_KEY_SEED`, so preview cookies survive rebuilds.

## Public Data API: `/api/v1`

`src/lib/api` is a thin skin over the data layer. `registry.ts` declares each endpoint (slug, description, which fields are public, which can be filtered), `filter.ts` applies the whitelisted query parameters and free-text `q`, `response.ts` builds the JSON envelope with CORS and cache headers, and `handler.ts` (`createCollectionHandler(slug, loader)`) wires them together and strips internal curation fields where they are not shown publicly. `/api/v1/openapi.json` and the `/developers` page describe it; `docs/api.md` and `docs/api-changelog.md` are the written contract. Data shaping belongs in `src/lib/data`, never here.

## Chatbot: `src/lib/assistant`, `src/components/assistant`

- `POST /api/assistant` streams Server-Sent Events from the Anthropic SDK (`runAssistantStream` in `stream.ts`). `prompt.ts` holds `PRODUCTION_PROMPT` and `PROMPT_VERSION`; `models.ts` pins the model IDs; `tools.ts` gives the model tools over a catalog (`catalog.ts`) built from the same data layer, plus page reading, search, geocoding, and the donation guide.
- `rate-limit.ts`: 50 requests per IP per day through Upstash's sliding window. Without Redis (local dev) requests are allowed and production logs a warning.
- Logging runs **after the response is sent** (`after()`): `conversation-store.ts` writes each turn to the console, the Airtable conversations table (`ADMIN_CONVERSATIONS_TABLE_ID`) and an optional webhook; `transcript-blob.ts` mirrors the full transcript to Blob. Chats not arriving on `aisafety.com` (dev, previews) are tagged internal.
- Admin: `/admin/chatbot/log` browses and annotates conversations (`PATCH /api/admin/conversations`), `/admin/chatbot/playground` tries prompt drafts and models against `/api/admin/test-run`. A daily cron, `/api/check-catalog`, checks that every table in the base is either in the catalog's `RESOURCE_TABLES` or its internal denylist.

## Analytics

- **Matomo:** the script in the root layout plus `MatomoRouteTracker` for client-side navigation. `src/proxy.ts` runs on every page request and reports fetches by AI assistants (ChatGPT, Claude, Perplexity, …) server-side, since they never run the script. Visitors can opt out on the privacy page (`useTrackingOptOut`).
- **First-party events:** the browser posts to `/api/track` (public, every field length-capped, per-IP throttle that fails open). `src/lib/analytics/events.ts` stores events in Upstash Redis, one list per calendar month, or in an `.analytics-dev/` NDJSON file when Redis is not configured. `/admin/analytics` aggregates per query. `themes.ts` groups typed chatbot questions with a Claude call, refreshed by a weekly cron or the dashboard button. Client helpers for click and filter tracking live in `src/lib/analytics.ts`.
- **Press page traffic figure.** `/media` shows last month's distinct visitors, the same number the dashboard gives for that month. `readLastMonthVisitors()` in `events.ts` works it out once per finished month (one full read of that month's events) and keeps it in Redis under `aisafety:analytics:monthly-visitors:YYYY-MM`; every later render is a single GET. With no store (contributor mode, CI) it returns null and the page leaves the row out.

## Admin: `src/app/admin`, `src/lib/admin`

- **Auth** (`auth.ts`, `access.ts`, `users.ts`, `users-store.ts`, `google-oidc.ts`, `session.ts`): people sign in with Google. `/api/admin/auth/google` starts an OpenID Connect authorization-code flow with PKCE (state, nonce and verifier sealed in a ten-minute cookie under `ADMIN_SESSION_SECRET`); `/api/admin/auth/google/callback` swaps the code for an ID token, checks its signature against Google's published keys plus issuer, audience, expiry and nonce, and only then looks the verified email up: first `ROOT_ADMINS` in `users.ts` (the owner, built into the code so an empty or unreachable store can never lock them out), then the managed list in `users-store.ts`. A hit sets a 7-day httpOnly session cookie holding just the email and timestamps under an HMAC. Access is looked up again on every request, so removing someone or unticking an area takes effect on their next click.

  There are no roles. Each person has one grant per area (`AccessFlags` in `access.ts`: `queue`, `playground`, `conversationLog`, `analytics`, `mapEditor`, `preview`, `newsletter`, `manageUsers`), and a grant is `false`, `'view'` or `'edit'`: `'view'` opens the tab, `'edit'` also lets its writes through. Areas that can change the live site (Queue, Map editor, Newsletters, Admin admin) carry an `edit` note in `ACCESS_AREAS`, which is what puts a "can edit" tick next to them on the Admin admin page; the others stop at `'view'` (`parseAccess` clamps). `ACCESS_AREAS` is the single list that drives the tab bar (`nav.ts`), the ticks on the Admin admin page and the gates. Layouts call `currentAccess()` once and let a view-only session in; the page hides what it can't do (a "View only" line instead of the action buttons) and the API routes ask the specific capability, read-level for reads and edit-level for writes (`canViewQueue` / `canReviewQueue`, `canViewMap` / `canEditMap`, `canViewNewsletter` / `canSendNewsletter`, `canViewUsers` / `canManageUsers`), never `isAdmin()`. Rows stored before 11 September 2026 hold booleans (a tick meant everything the tab could do) plus a separate `newsletterPreview`; `users-store.ts` reads every row through `parseAccess`, which maps `true` to the area's top grant and `newsletterPreview` to `newsletter: 'view'`, so nothing needs migrating and the next write stores the new shape. `currentAdmin()` returns who is signed in for attribution. Changing who can sign in additionally needs `hasFreshSession(SENSITIVE_FRESH_SECONDS)`: a session Google minted within the last 30 minutes, which a stolen cookie cannot produce on its own. Approving or stopping a newsletter send needs the same, within `NEWSLETTER_FRESH_SECONDS` (4 hours), and an approver opening `/admin/newsletter` with an older session goes through Google first. Env: `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET` (Google Cloud console, project "AISafety admin"), `ADMIN_SESSION_SECRET` (rotating it signs everyone out). Registered redirect URIs: production, `ai-safety-com.vercel.app` and localhost dev ports; branch preview deployments cannot sign in with Google.

  **Admin admin** (`/admin/users`, `manageUsers` area; its `'view'` grant shows the list, `'edit'` changes it) is where people are added by Google email, given tabs or removed; their display name is whatever Google reports at their first sign-in (`recordSignIn`), never typed in. Everyone but the root admins lives in `users-store.ts`: one small JSON document in the same Upstash Redis the analytics use (`admin:users`, plus an `admin:last-sign-in` hash the Google callback updates), or `.admin-dev/users.json` on a laptop without Redis. `/api/admin/users` (GET/POST/PATCH/DELETE) validates input with `validateUserInput`; writes need the fresh session above, nobody can edit a root admin, remove their own login or take the edit grant off their own Admin admin access, and every person must keep at least one tab. A write refused for a stale session (401 `reauth`) makes the page stash its ticks, the add form and that request in `sessionStorage` (`users-pending.ts`, honoured for an hour), leave for Google with `next=/admin/users?resume=1`, and on the way back restore the ticks and send the request again; without the marker (a later visit) only the ticks come back. Nobody needs to send their email first: a Google account that isn't on the list gets an "Access requested" screen (`/admin/login?requested=1`, the address carried in a sealed five-minute cookie rather than the URL) and the callback records the request (`admin:access-requests`, capped at 100, one entry per email with a try count). Requests appear at the top of Admin admin with a badge on the tab; approving is a normal add that keeps the Google name and clears the request, `DELETE /api/admin/users/requests` dismisses one. `mail.ts` emails the owner when a request is recorded and the person when they are approved or added, through the same kind of Google Apps Script web app the hackathon forms use (source in docs/admin-mail-script.md; env `ADMIN_MAIL_SCRIPT_URL` + `ADMIN_MAIL_SECRET`, off without them); both run in `after()` so nothing waits on them. The script only delivers a "request" mail to the owner's own address, so a leaked secret can at most send the fixed approval template.

  **Passwords are gone** (retired 4 September 2026). `POST /api/admin/auth` no longer exists; `DELETE` there is sign-out. The old `aisafety_admin` cookie is only ever deleted.

- **Who annotated what.** Every rating, label and notes change on `/admin/chatbot/log` is attributed: `updateConversation` reads the row, works out what actually changed (`annotation-log.ts`), appends one line per change to the row's **Review log** field (`2026-09-05 11:42 UTC · Name · rated Good`) and keeps the current verdict's author in **Reviewed by**. Notes are signed entries in the **Notes** field (a `2026-09-05 12:10 UTC · Name` header line, then the text; `parseNotes`/`appendNote`), added one at a time from the log page, and anyone signed in may delete any entry (`removeNote` checks the entry still sits where the page saw it; the deletion is logged with the note's author); text from before signing existed shows as an unsigned block. The log page shows all of it. Names come from the Google sign-in.

- **Map editor.** `/admin/map` (`mapEditor` area; `'edit'` to move anything, `'view'` shows the same map and side panel with nothing to drag, place or resize, `applyChange` being the one place every change passes through) lets the owner drag logos on the Field map and change a logo's size. It writes to Airtable through `/api/admin/map` (GET live records, PATCH one change). It is deliberately a **copy** of the public map's rendering, not a shared component: `map-geometry.ts` mirrors the constants in `src/app/map/D3Map.tsx` and `map-geometry.test.ts` fails if they drift. The editor reads Airtable directly with `cache: 'no-store'` (unpublished rows included, Hide? rows excluded), never through `fetchAirtableRecords`, and never revalidates anything, so `/map`'s data path, cache and bundle are untouched. The only fields it can write are `x` and `y` together, or `Scale` as one of its existing options (`map-editor-core.ts`; any other key in the request body is rejected). Publish? and Hide? stay in Airtable.

- **Queue.** `/admin/queue` (`queue` area; `'edit'` to decide anything, `'view'` shows the same inbox with a "View only" line in place of Accept / Reject / Undo and every field read-only, `act()` a no-op) is one review inbox for everything waiting on the owner: a person's email or Discord request, a Broom flag, a rulebook edit written from earlier reject reasons, a Comb suggestion. Rows live in the Airtable table **Queue** (`tblonlKwIFJ7Aa8QN`, `src/lib/admin/queue.ts` holds the field ids) and are written by the bots on the owner's Mac (`~/Queue`); the site only lists them and carries out decisions through `/api/admin/queue` (GET list, POST `{id, action}` with `accept` / `reject` / `revise` / `undo`). The list is the rows and nothing else, so it lands in about a second; the page then fills the logos in through `POST /api/admin/queue/logos` (the site's catalog, plus one read per table for unpublished targets: seconds when the catalog's cache is cold, which every accept makes it) and builds the cards through `/api/admin/queue/previews`, both in the background. The list opens with the items Fable is answering, or has answered since the owner last looked, whatever their kind; then **Urgent** (`queue-urgent.ts`): an addition whose start date or deadline is within four days, a change on a listing starting or closing within two weeks (the logos lookup also returns published events' and trainings' dates for that), or a fix that takes down a closed listing or corrects a link, a date or an application status, never one Fable says to skip; then the rest by source and resource page, oldest first so the old pile rises. The page reads the list again once a minute while the tab is in view and the moment it comes back into view, with `?sync=1`: the API then first closes the open Add rows whose record was deleted, published or hidden in Airtable itself (the Mac worker's sync, done at once instead of on its five-minute pass; it writes, so it takes the edit grant). The row carries the proposal as JSON: for an **Add** the proposed record's fields (accept ticks `Publish?` on the target record, plus any values edited on the page); for a **Change** a list of `{field, from, to}` (accept writes the `to` values by field NAME and deletes the Broom flag row; reject deletes the flag row too); for a **Rule** a diff (accept only marks the row Accepted, the Mac worker patches the file). Every accept re-reads the row and refuses one already decided (409), then calls `revalidateTag('airtable-records', 'max')` so the public pages refresh within a few minutes. Reject takes an optional reason (the page offers chips Fable wrote at intake, or one can be typed); a rejected suggestion is deleted by the Mac worker 24 hours later, which is the undo window. `Publish?` and `Hide?` can never be set through edits or proposals (`sanitiseEdits`, `PROTECTED_FIELDS`). Nothing auto-applies, ever. An emailed request (Source Email, written by the owner's inbox bot) also carries a reply draft in the owner's voice: the page shows it editable, an accept writes the approved text to the row, and then the page calls a small **agent on the owner's Mac** (loopback HTTP, port from `QUEUE_AGENT_PORT`, default 8790) to save it as a Gmail draft at once, never to send it. `GET /api/admin/queue` hands the page `{ port, token }` for that call, the token sealed with `QUEUE_AGENT_SECRET` (both sides hold it; unset = no agent, the Mac worker saves the draft on its next pass). The agent only acts on rows Airtable says are already accepted, so the token can do nothing the queue has not approved. A Discord request (Source Discord, written by the hourly intake on the owner's Mac, `~/Queue/discord_intake.py`, from the Matrix bridge) carries a reply draft in Fable's own voice under a "From Fable:" line and the person's Discord avatar beside what they wrote; the draft sits next to the message as an exchange. Replies from the Queue are drafts, never sent (owner's rule, 14 Sept 2026): the page offers Copy reply and Open on Discord (the toast, the card, the Done list) and the owner pastes and sends it himself, as an emailed request's reply stays a Gmail draft. The page opens the item named in a `#rec…` hash, which is how the bot's "Queued:" links land on the right card, and it keeps the hash in step with the item in focus (replaced, never pushed) so the address bar is always a link to that one suggestion.

- **Newsletter approval.** `/admin/newsletter` (`newsletter` area; `'edit'` to approve, `'view'` opens the same page read-only — drafts and previews, no Approve button, send API refuses — for a design reviewer or a second pair of eyes) is the approval step for the weekly newsletters. The pipeline on the owner's machine renders a draft into a branded email and creates a **draft** ActiveCampaign campaign whose message carries a hidden content marker (`<!--aisafety-issue:<checksum>-->`). The page lists those drafts via `/api/admin/newsletter` (GET), re-running the pipeline's own checks on each: still a draft, wired to exactly one list (per-list one-click unsubscribe depends on it), one message, marker present and matching a fresh checksum of the HTML (`contentDigest` in `newsletter.ts`; `newsletter.test.ts` pins it to the pipeline's fixtures). A missing marker means someone saved the email in ActiveCampaign's visual designer, which wipes injected HTML, and the page refuses to send. The preview is the stored HTML in a sandboxed iframe (`/api/admin/newsletter/preview?draft=ID`; `draft=` because ad blockers refuse `campaign=` URLs, and CSP `frame-ancestors` rather than X-Frame-Options, which would reject the sandbox's opaque origin). Approving (POST) re-verifies, then schedules the send through ActiveCampaign's legacy v1 API, the only one that can schedule, by creating the sending campaign from the verified message five minutes out on the real lists (two on the test lists) and deleting the draft shell (after a whole-list send or the last wave; see Waves). **Send safety** (29 Sept 2026, before the Substack readers are imported): an approval takes an Upstash `SET NX` lock per list + issue, whether it sends the whole list or a wave (`aisafety:newsletter:approve-lock:<list>:<issue>`, 15 minutes, released only when it fails before `campaign_create`), so two tabs or two approvers can't both send, and card edits to the issue wait while it is held; it reads the campaigns again, uncached (`orders[id]=DESC`: ActiveCampaign ignores `orders[cdate]`), right before the create, and any campaign of the same issue on the list counts as already sent unless it is a draft or was stopped before reaching anyone (unknown statuses count as sent); any error once the create has been asked for answers 202 "may have been scheduled – don't press again". `sendChecks()` refuses emails without the unsubscribe link or postal address, with a sender off news.aisafety.com or not the list's own (Events 6, Training 7, Funding 8; test lists 4/5 exempt; no other list), a click-counter link whose Blob list is missing or broken, HTML over 90 KB, or an older issue still waiting on the list, and makes the approver tick edited card text, leftover words (TEST, TODO, `{{`) and dates already past before the send button works (the server checks every tick came back). Right before the create it reads the email again and refuses if it changed since the checks (an edit from another tab). After the create it reads the campaign back and deletes it at once if link tracking came back on. Only production (`VERCEL_ENV=production`, and never a dev server, even with that value pulled into `.env.local`) may approve, or edit drafts on, lists 6/7/8; while `NEWSLETTER_WARMUP` is on, a send to more than `MAX_UNSEGMENTED_SEND` (50) people must name a wave. Every real-list approval is recorded for the send watcher: `aisafety:newsletter:approved:<campaignId>` (JSON, no expiry) and the sorted set `aisafety:newsletter:approved` (score = approval time); the approver's name is logged and returned, and the owner gets an email only when an approval may have gone out despite an error (the 202 above: `notifyApproval`, the admin mail script's owner-only `digest` kind, sent after the answer), never for an ordinary approval (Bryce, 2 Oct 2026). **Waves and Stop** (29 Sept 2026): the first sends to the imported readers go out in warm-up waves. `~/Newsletter/waves.py` tags the contacts and makes one ActiveCampaign saved segment per wave, "Newsletter wave 1" … "Newsletter wave N (everyone else)" (test lists 4/5: "SWEEP TEST wave …"); the page finds them by name (`GET /api/3/audiences`), checks their conditions (tag k; the last one none of the tags), counts each on the list (`contacts?listid&status=1&tagid`; the last is the rest) and offers the next wave. A wave's campaign carries the segment (`segmentid`), is named "<issue> · wave k/N", and is read back and deleted at once if ActiveCampaign didn't keep the segment or the read back fails; Recent sends flags a wave-named send without a segment. Waves go in order, one at a time; wave k+1 needs wave k sent (status 5) and `WAVE_MIN_GAP_HOURS` (18) since it finished, and the send watcher's verdict on it (`aisafety:newsletter:health:<id>`) not red — or a typed reason, which is logged and recorded. A wave stopped after reaching people ends the issue's run. The draft stays until the last wave, and card edits wait while a wave made from it is going out. Recent sends and the Analytics tab group an issue's waves (clicks are counted per issue). Recent sends' Stop buttons post to `/api/admin/newsletter/stop` (same approver and fresh-session checks as Approve, a confirm step, one press per campaign at a time): a scheduled or held send can be canceled (deleted: nobody gets it), a sending one paused, a paused one stopped for good or resumed (resume on the real lists from production only); a send that hasn't finished stays on Recent sends however old it is, so it keeps its buttons. Every newsletter POST route answers only the admin page itself: a request whose `Sec-Fetch-Site` isn't `same-origin` (or, without it, whose `Origin` isn't this site) gets a 403, since the Lax session cookie still rides along from another subdomain of aisafety.com (`isSameOriginRequest` in `src/lib/admin/origin.ts`). **Test copies** (29 Sept 2026): Send test (approvers) posts to `/api/admin/newsletter/test`, which runs the same checks and then mails the draft through ActiveCampaign's own test send (v1 `campaign_send` with `action=test`) to the signed-in approver's address — taken from the session, never from the request — so it lands in one inbox with “TEST: ” before the subject and nothing goes to the list. The page holds Send test and Approve & send back while an edit is still saving, so neither goes out without it. **Reordering** (10 Sept 2026): the renderer wraps every listing card in `<!--card:gN:KEY-->…<!--/card-->` (gN = section, KEY = the Airtable record id) and ends the email with a base64 JSON manifest (`<!--aisafety-cards:…-->`: sections, card titles, and the plain-text version as keyed segments). The page's Reorder panel (shown beside the preview for approvers; drag and drop, arrow keys on a focused row as the keyboard route; a card never leaves its section) posts the new order to `/api/admin/newsletter/reorder`, which re-verifies the draft, moves the card blocks, rebuilds the text from the manifest, re-stamps the marker and writes the message back through the v3 API — `reorderHtml` in `newsletter.ts` is the same algorithm as the pipeline's `render.py reorder_cards()`, and a rebuild on the owner's machine reads the live order first so a manual reorder survives later edits. **Editing card text** (25 Sept 2026): every piece of text on a card sits between `<!--f:NAME-->…<!--/f-->` markers (`title`, `m0`… the lines under it, `desc`, `b0`… the rows at the bottom; rows carry their icon, `<!--f:b0:money-off-->`, which names them in the editor). Each row in the Reorder panel has an Edit button that opens every field of the card (plus a funding card's "Consider applying if" line). Text saves by itself (900 ms after the typing stops, or when a box loses focus; one save at a time) by posting the changed fields to `/api/admin/newsletter/card`, which rewrites them the same way as a reorder (`setFieldsHtml`, same algorithm as the pipeline's `render.py set_fields()`, pinned by a byte-for-byte fixture in `__fixtures__/newsletter-card-edit.json`). The manifest keeps a field's text as built under `o` on its first edit, which is how the page shows "edited" and offers Pen's text back, and how a rebuild on the owner's machine carries the edit over unless Pen changed that text since. Each save reloads the preview at the same scroll position: the preview route injects one nonce-allowed script into the sandboxed frame (still no `allow-same-origin`) that posts its scroll position up and scrolls to `#y=` after a reload. When the owner presses "Use this description on the site too", a separate call to the same route (`listing`) writes the description to the listing's Description field in Airtable (`newsletter-listing.ts`: the record is looked up in the Events, Training and Funding tables by the card's record id, then a record comment notes the source) — the only Airtable write the newsletter page makes. **Click counting** (28 Sept 2026): ActiveCampaign's own click tracking is off (its tracker dropped about half the connections), so the pipeline points every link of an email at `/api/nl/<list>/<n>` and saves the email's links as one JSON list on the site's Blob store (`newsletter/links/<list>.json`, named by its content so it never changes once written). The route never lets one bad entry break a whole list (only that link falls back to the homepage), gives the Blob read 2.5 seconds including Next's fetch cache (a reader waits 4 seconds at most), keeps a copy of each list in Upstash (`aisafety:newsletter:links:<list>`, used only while its hash still matches its name), skips link scanners that open three links of one list within 10 seconds, and sends truncated or extended `/api/nl` paths to the right link or the homepage (`src/app/api/nl/[[...rest]]`). Never delete anything under `newsletter/` in the Blob store. The public route (`src/app/api/nl/[list]/[n]`) looks the link up, redirects, and after the redirect counts the click in Upstash (`aisafety:newsletter:clicks:<campaign name>`, one field per link; a file under `.analytics-dev/` locally) — anonymous, per campaign and link. Only links in our own lists are followed, so the route can't be used as an open redirect; link checkers, HEAD requests, the admin preview (`?p=1`, added by the preview route), anyone signed in to the admin (checked after the redirect: the team clicking through a test copy or their own copy of an issue) and, once Send test has mailed a copy of an issue, every click on it until the issue's first send or wave is due (`aisafety:newsletter:test-copy:<name>`, 30 days, and `aisafety:newsletter:sends-from:<name>`, both written once; a test copy's links are the issue's own, so time is the only way to tell them apart) aren't counted; an unknown link goes to the homepage. The Recent sends table shows each send's clicks with a per-link breakdown (`src/lib/newsletter-clicks.ts`). **Web version** (30 Sept 2026): each issue's "View in browser" link opens `/newsletter/<key>/<issue>` (`/newsletter/events/week-41-2026`, `/newsletter/funding/issue-21-2026`), the email as sent on a page of its own, instead of ActiveCampaign's web copy (a share bar, a white frame and its branding). `src/lib/newsletter-web.ts` maps the address to the campaign name and back; the pipeline's `render.py web_url()` writes the same address. The public route (`src/app/newsletter/[key]/[issue]/route.ts`) shows an issue only once a campaign of it has reached readers on its real list (`sentIssueHtml`: sending, sent, or paused or stopped part-way; never a draft, a scheduled send or a test-list send), keeps that email in the Blob store (`newsletter/web/<key>/<issue>.html`, written once, never changed) so later views and links in old emails need no ActiveCampaign read, and leaves out the footer between the pipeline's `<!--web:hide-->` markers, the content marker and the manifest. The page runs no scripts (CSP `default-src 'none'`), isn't indexed, and is CDN-cached for a day (a missing issue for 30 seconds). Clicks on "View in browser" are counted like any other link. **Lined up** (8 Oct 2026): the page's first block counts, per newsletter, the listings Pen would pick up as new if it drafted the next issue now (`newsletter-lineup.ts`, same rules as Pen): Events and Training listings on the site, added in the last month, with Newsletter unticked; Funding listings accepting applications now that weren't when the last Funding issue was approved, plus (as a second number) those whose applications close in the next two weeks. That baseline is `aisafety:newsletter:funding-baseline` (the accepting record ids, written after an approval on list 8, kept for later waves of the same issue); before the first one, Pen's snapshot after Issue #22 stands in (`newsletter-funding-seed.json`). Listings already in a waiting draft are left out. Env: `ACTIVECAMPAIGN_URL`, `ACTIVECAMPAIGN_KEY` (production only).

## Other integrations

- **Newsletter signups** (8 October 2026): the box at the top of `/events` and `/training` (`NewsletterSignup` with a `newsletter` key) posts to `/api/subscribe`, which hands the address to that newsletter's double opt-in form in ActiveCampaign (Events list 6, Training list 7) with a server-side POST to the account's form endpoint, `proc.php` (`src/lib/newsletter-signup.ts`; the forms' public values sit in `AC_FORMS`, and a form left unset answers 503 without sending anything). ActiveCampaign emails the reader a link to confirm. Only a clear thank-you from ActiveCampaign counts as a signup, and the logs never carry the address. Bot protection (`src/lib/newsletter-signup-limits.ts`, Upstash) is built never to stop a person: a hidden honeypot field, 30 signups an hour per IP, at most 3 sends per address and newsletter a day, an email to the owner once a day passes 100 signups and a stop above 1,000, and every limit skipped while Upstash is down. No CAPTCHA. How signups end shows on the Analytics Newsletters tab. The `/funding` box and the footer's Funding and Updates links still go to Substack.
- **Hackathon forms** (`/hackathon`, `/hackathon/details`) post to Google Apps Script, which appends to a private Sheet and emails the applicant. See `docs/hackathon-signup.md`. Env: `HACKATHON_SCRIPT_URL`, `HACKATHON_FORM_SECRET`.
- **Suggest-a-listing and feedback forms** are Airtable forms opened from the site (`ContributeButtons`), not app code.
- **Press kit** (`/media`): the logos are static files in `public/press`. The three screenshots, the "download everything" zip and a small `manifest.json` (refresh date, zip size) live in Vercel Blob under `press/`, at fixed public addresses (`PRESS_BLOB` in `src/app/media/content.ts`). They are re-shot from the live site every Monday by Media Shots, a small job outside this repo (the owner's `media-shots` tool: headless Playwright, then `put` with `allowOverwrite`). It uploads nothing unless all three pages loaded properly, so a broken page never replaces a good screenshot. The page reads the manifest with an hourly cache and still renders without it.

## Scheduled jobs (`vercel.json`)

| Path                          | Schedule          | Purpose                                              |
| ----------------------------- | ----------------- | ---------------------------------------------------- |
| `/api/check-rebuild`          | every minute      | rebuild when published Airtable rows changed         |
| `/api/check-catalog`          | daily 09:00 UTC   | every Airtable table is known to the chatbot catalog |
| `/api/admin/analytics/themes` | Mondays 07:00 UTC | regroup chatbot questions into themes                |
| `/api/admin/newsletter/watch` | every 10 minutes  | watch newsletter sends; email the owner on problems  |

Cron routes check the `Authorization` header against `CRON_SECRET` when it is set; the newsletter watcher refuses every request when it isn't.

The newsletter watcher (`src/lib/admin/newsletter-watch.ts`, 29 Sept 2026) only reads ActiveCampaign. It emails the owner once per problem on the real lists (a send held for review, paused, stopped, late or slow; a send that didn't come through the approval page or has no wave during the warm-up; a pipeline draft left waiting; the API failing; the account's limit or status changing; the contact count near the cap) and, 18 hours after each send on Events or Training, a green/amber/red health check. Open problems show as a banner on /admin/newsletter (`GET /api/admin/newsletter/alerts`). It tries at most 4 emails an hour and 20 a day, and a problem that comes and goes within 6 hours is emailed once. State lives in Upstash under `aisafety:newsletter:watch:*` and `aisafety:newsletter:health:*`; outside production a run is dry (no writes, no email), since every environment shares that database.

## Testing

Unit tests run with Vitest (`npm test`; files `src/**/*.test.ts`, node environment, `@` alias resolves to `src`). Pure modules only, nothing that imports Next, d3 or the DOM; tests sit next to what they test. `npm run build` runs the suite before building. Browser smoke tests (`e2e/smoke.spec.ts`, Playwright, `npm run test:e2e` against a production build) open every public page in Chromium, fail on any uncaught error or console error, check that listing pages show listings and the map draws its logos, and call every Data API endpoint. CI (`.github/workflows/ci.yml`) runs type-check, lint, unit tests, a production build and the smoke tests on every pull request and push to `main`, with no secrets: the build runs in contributor mode against the live site's public data. Visual review of design changes is still done by hand.

## Deployment

Vercel. Every push to `main` deploys production; every branch gets a preview deployment. Environment variables live in the Vercel project. Blob and Upstash Redis come from the Vercel Marketplace integrations, which is why the Redis variables carry the legacy `KV_REST_API_*` names. Analytics and the chatbot log treat only `aisafety.com` as real traffic, so previews and localhost never pollute the data.
